## Research authoring and publication

1. Add a draft to `content/research.json`, a version-controlled JSON array. Each record has `slug` (stable, unique, lowercase letters/digits/single hyphens, maximum 100 characters), `title`, `summary`, `state` (`draft` or `published`), `publishedAt` (valid UTC calendar date, YYYY-MM-DD), an explicit `classification` (`standard`, `negative-result`, `product-experiment`, `analysis-proposed-evaluation` or `technical-explainer`), `byline` and a non-empty `body`. Classification comes from metadata, never title or body inference; the `analysis-proposed-evaluation` class displays as “Analysis / proposed evaluation”, while `technical-explainer` remains outside the catalogue, RSS and sitemap. Draft publication dates are proposed dates only; confirm the actual date when publishing. Never put secrets in this repository or in an article draft.
2. Use body blocks: `{"type":"paragraph","text":"..."}`, `{"type":"heading","level":2,"text":"..."}` (level 2 or 3), `{"type":"list","items":["..."]}`, `{"type":"code","text":"..."}`, and `{"type":"link","text":"Source title","href":"https://..."}`. Approved structured articles also support the exact `evidence-map`, `shutdown-claim-card`, `comparison-table` and `self-check` schemas enforced by the build generator; do not improvise keys, statuses or source sets. Text is React-escaped. Links allow HTTPS, local absolute paths or simple fragment IDs, not executable protocols, embedded credentials or raw HTML. MDX and executable content are not supported. Add figures only when a real approved article needs them, with proportionate rights/accessibility review and a scoped schema change.
3. The relevant author/technical owner reviews claims, sources, limitations and reuse rights. Obtain explicit approval for the truthful byline (including owner approval for organizational `noqt Research`; never imply fictional staff). Growth reviews wording and hierarchy. Record the exact candidate and these decisions in private evidence; set `approvals` to `{"technical":true,"editorial":true,"byline":true}` only after those reviews. Reset affected approvals after substantive edits. Flags document decisions; they do not authenticate reviewers.
4. Deliberately set `state` to `published` and confirm `publishedAt` is the actual publication date. Run `npm test` and `npm run lint`, review the rendered candidate and publish through the existing Site release workflow. `npm run dev` and `npm run build` regenerate `app/research/published.generated.json`; never edit it directly or bypass the generator with a direct vinext command. Restart development after content edits. Only approved non-future articles are projected into that generated file; source drafts, review notes and flags are never imported by public code. Invalid content closes the build and clears a stale generated catalogue. Do not deploy any old build after a failed build.
5. Future dates are excluded at build time against the Australia/Sydney editorial date, not automatically scheduled. Rebuild/review/publish deliberately when ready; there is no publication scheduler. Articles sort newest first, then slug for same-date ties. Routes are `/research/<slug>`; keep published slugs permanent.
6. For a substantive correction retain the original `publishedAt`, add a valid non-future `updatedAt` on or after it, and a short `correction` explaining the change. Re-review and release. To unpublish, change state to `draft`, regenerate, test and redeploy; its route then returns HTTP 404 and it disappears from index and deployed bundles. This cannot retract copies already cached or downloaded by others.

The synthetic fixture exists only in tests. Tests exercise the actual shared article renderer, slug lookup and publication boundary; fixture content never enters the public catalogue. Production worker tests cover the published Research index, the first real article's direct URL, metadata, source links and Research → article → back journey, plus unknown/unpublished 404s and deployable-bundle exclusion. Verify that journey on each exact candidate and live site. The public sitemap lists only the explicit static-page allowlist and eligible published research; article `lastmod` uses its publication or correction date, while static pages omit it because no source publication date is maintained. Draft, future, private, product-experiment, technical-explainer and Principia content remains absent. These routes aid crawler discovery; they do not establish indexing, traffic or adoption.

Principia Periculi is temporarily excluded from the public website at the Founder's request on 8 September 2026. Preserve the underlying work and history; do not restore its card, links, metadata or structured-risk proposition without a new publication decision.

## Yumi continuity Threadmarks

Yumi continuity has a v1.1 Threadmark mode for an already-authorized agent
passing a small, explicit revision ledger between tools or domains. It checks
all supplied current heads and live assertions, preserves assertion/revision
and opaque source identifiers, and marks each required key as stable, missing,
withdrawn or conflicting. A READY result means only typed consistency inside
the supplied ledger; it does not authenticate sources, establish truth,
completeness outside the input, permission or safety.

[Inspect the v1.1 Threadmark resolver, schema, examples and tests](yumi/continuity/v1.1/README.md).
It runs offline with Python 3.11+ and the standard library. The receipt is
bounded, deterministic and has no network, telemetry, private-memory access,
source dereference or implicit ledger write. A conflicted, incomplete or
oversized receipt remains a review/detail-required result rather than a
truncated READY result. The neutral Yumi capability capsule is inert metadata,
not an instruction or authorization.
